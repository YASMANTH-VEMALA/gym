# QR management

Migration 010 adds QrCredential with composite tenant/target foreign keys, one credential per member or branch, kind/target/state constraints, indexed unique SHA-256 token hashes, and RLS. Existing rows are untouched.

Tokens are 256 random bits, encoded as 43 base64url characters. QR payloads contain only the public web origin and an opaque token in a URL fragment. They contain no member identifiers or personal data. Database lookup uses SHA-256. Reprinting an existing card requires recovering its token, so an AES-256-GCM encrypted copy is stored separately from the lookup hash. Encryption authenticates the credential ID and business ID as additional data. The key is server-only `QR_ENCRYPTION_KEY`, exactly 32 random bytes in base64, independent of Supabase credentials. Back up the key securely with your server secrets; losing it requires rotating and reprinting cards. Do not replace it casually. A wrong key produces a recoverable error without logging cryptographic input. Revocation removes the encrypted token; rotation replaces both hash and ciphertext.

Configure `WEB_ORIGIN` as your HTTPS application origin (HTTP allowed only for localhost). Generate a key using a cryptographic random generator and place it directly in your secret manager, never source control. `.env.example` contains no key. QR images use the server-side [node-qrcode library](https://github.com/soldair/node-qrcode).

Owner/Admin endpoints under `/api/v1/businesses/:businessId/qr`: GET paginated metadata, POST generate or rotate, GET `:id` for authorized image/reprint, POST `:id/revoke`, POST `branches/ensure` to prepare missing active branch credentials, POST `resolve/member`. Generation is idempotent unless explicitly rotating. Preparing branch codes never revives revoked credentials. Active targets are validated during generation, viewing, and resolution; archived or inactive targets cannot resolve. Business access is enforced independently of possession of a token.

POST `/api/v1/public/qr/branch` accepts a token in the body and returns only business name and branch name. Tokens are never path or query parameters. `/join` strips the URL fragment immediately and keeps it only in tab-scoped session storage during registration. `/q/member` similarly retains a scan while staff authenticate, then requires an authorized business and active branch before resolving and checking in the member. The scan uses the same attendance service as manual check-in, so active-membership validation, branch scoping, business-calendar dates, audit events, and one-record-per-day deduplication stay consistent. Success/cancellation clears the scan. Responses are no-store. Request bodies, bearer tokens, QR tokens, generated image responses and credential ciphertext must never be added to request/audit logs or analytics.

`/admin/qr` provides member/branch sections, paginated search, generation, preparation of missing branch codes, view/download, rotation confirmation and revocation confirmation. `/admin/qr-management` remains a compatibility route. Changes audit QR_GENERATED, QR_ROTATED or QR_REVOKED using identifiers only.

Attendance supports both manual staff entry and member-card QR check-in. Branch registration remains separate and connects to the member portal.

Tests cover random token shape, hash/encryption persistence, secret-free metadata/audits, anonymous branch resolution with minimal data, member resolution authorization, tenant isolation, forged targets, idempotent generation, rotation, revocation, preparation retries, inactive targets and authenticated browser view/download.
