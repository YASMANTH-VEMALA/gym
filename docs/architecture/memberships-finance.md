# Memberships, payments and dues

Membership assignment snapshots the selected active plan's name, integer minor-unit price, and calendar-day duration. The active member, active branch, and plan must belong to the authorized business, and the plan must cover that branch. End dates are inclusive. Non-cancelled periods cannot overlap for the same member and branch. A new period provides renewal history. Business-row locks serialize assignments; idempotency keys reject changed payloads. Cancellation preserves the fee obligation and payment history; it is not a refund or debt waiver.

Migration 007 adds Membership without altering existing records. Migration 008 adds Receivable and Payment and backfills exactly one receivable per existing membership, using the agreed price and start date. New assignments create both records in one transaction. Composite foreign keys bind financial records to the same business. New tables enable RLS; browser clients do not receive direct table privileges.

Outstanding = agreed original amount minus the sum of RECORDED payments. Money uses integer minor units throughout storage, validation, arithmetic, and API contracts. Payments are manual CASH, UPI, BANK_TRANSFER, CARD or OTHER records. Their payment date is a business calendar date and cannot be in the future. Collection metrics use non-void payments dated in the current business calendar month. All-time outstanding balances are independent of that collection window.

An explicit promise date always replaces the original due date for overdue calculation until staff change or clear it. Original due dates never change. Status precedence is VOID, PAID, OVERDUE, PARTIALLY_PAID, OPEN. A positive balance is overdue strictly after its effective expected date, computed in the business timezone. Promised-this-week means Monday through Sunday. Dues metrics apply the visible dues filters; payment history independently shows all records for the selected business, branch, member or membership.

Owners and Admins can record manual cash payments, void with a required reason, and set or clear promises. The API retains the original payment-method enum for historical imports and reports, while the operational payment form records CASH. A business-row lock serializes financial writes, including concurrent payments, so each transaction checks the latest valid payment sum. Idempotency keys are unique within a business and compare all material payment fields. Exact retries return the original record, even if subsequently voided. Void is idempotent, never deletes history, and restores the outstanding balance. Payment corrections require void and a new payment. No online gateway, refund, invoice, or automatic cancellation write-off is implemented.

The payment ledger accepts an inclusive payment-date range and method filter. The admin UI defaults that range to the current business month, exposes prior months with a month picker, and shows recorded cash totals and counts per branch. Selecting All Branches provides the owner-wide rollup; selecting one branch applies the same scope to dues, history, totals, and pagination.

Endpoints under `/api/v1/businesses/:businessId`: `GET/POST memberships`, `GET memberships/:id`, `POST memberships/:id/cancel`, `GET dues`, `PATCH dues/:id/promise`, `GET/POST payments`, `POST payments/:id/void`. Each request verifies the Supabase user and business access; referenced members, branches, memberships, receivables and payments are scoped independently. Financial changes audit only actor, business, action and target identifiers, without financial request payloads.

Frontend routes `/admin/memberships`, `/admin/memberships/new`, `/admin/memberships/:id`, `/admin/dues` and `/admin/payments` share connected membership/payment views with member detail tabs. Payment confirmation shows original fee, paid, outstanding, entered amount and remaining balance. Failed submissions retain the original key and payload for safe retry. Voided records remain visible. Member lists show actual dues. Dashboard shows actual collections, dues, upcoming renewals and member growth; attendance is a separate unavailable dependency.

Validation: integration coverage includes legacy membership backfill/preservation, membership snapshots, overlaps, tenant boundaries, exact and changed retries, partial/full payments, concurrent overpayment rejection, payment voids, promise dates, recalculated balances, filtered histories and dashboard totals. Playwright covers creating the member and plan, assignment, partial payment, promise date, void, dashboard and mobile dues layout.
